# Java Blueprints

Веб-среда для разбора Java-проектов в граф, поиска дефектов, редактирования AST, оптимизации и проверки поведения. Клиент React + TypeScript + Monaco + React Flow, сервер Java 21 + Spring Boot + JavaParser.

## Запуск веб-демо

Воспроизводимая сборка, предусмотренная слайдом 11 ТЗ:

```sh
docker compose up --build
```

Открыть http://localhost:3000. API доступен на http://localhost:8080, OpenAPI — http://localhost:8080/swagger-ui.html. Публичный хостинг не настроен.

Для разработки нужны JDK 21, Maven или Maven Wrapper, Node.js 22 и npm:

```sh
cd server
./mvnw spring-boot:run
```

В другом терминале:

```sh
cd client
npm ci
npm run dev
```

В Windows: `server\mvnw.cmd spring-boot:run` или `scripts\run-windows.bat` после установки npm-зависимостей. JDK должен быть указан в JAVA_HOME. Если Java уже установлена, но не находится в PATH, задайте JAVA_HOME на каталог JDK.

Без сервера доступны редактор и интерфейс; компиляция, анализ, преобразования и Quality Gate требуют API. Локальной проверки поведения в браузере нет. Профиль `stub` предназначен для разработки интерфейса и не подтверждает поведение Java-программ.

## Полный сценарий

1. Нажать «Демо ТЗ» для встроенного монолита или импортировать один/несколько `.java`. Можно повторно импортировать `java-project.json`, сохранённый кнопкой «Экспорт».
2. Добавить входные данные кнопкой «Загрузить .in». Для пустого списка тестов сервер выполняет один сценарий с пустым stdin, отображаемый как `default`.
3. Выбрать метод и дефект. Карточка показывает исходный метод, реальное предложение анализатора, оценку Big-O и рекомендацию. Если предложения нет, интерфейс явно сообщает об этом.
4. «Исправить дефект» применяет один шаблон; «Оптимизировать» — пакет шаблонов и декомпозицию. Оба пути сравнивают результат с исходным проектом через Quality Gate до замены файлов.
5. Проверить результаты и консоль. `PASSED` требует `allPassed === true`, `behaviorMatched === true` и успешных результатов всех отправленных тестов. Ошибки компиляции показываются целиком. Ошибка проверки сохраняет исходный проект.
6. Экспортировать Java-файл или весь многофайловый проект в JSON. Все файлы дерева отправляются для графа, анализа, мутаций, сборки, запуска и проверки; переключение вкладок сохраняет правки. Импортированный проект и исходный набор файлов сохраняются в localStorage.

На холсте удаление/вставка/перенос оператора меняет AST; сервер проверяет компиляцию. После ручных правок следует отдельно нажать «Запустить тесты». «Дебаг» — визуальный обход узлов, без выполнения JVM и просмотра переменных.

## Примеры и входные данные

| Пример | Назначение | Входные наборы |
| --- | --- | --- |
| `samples/Main.java` | Заказы, коллекции, вложенные циклы, длинные методы | `samples/inputs`, 12 файлов |
| `samples/stress/Main.java` | 939 строк: заказы, аналитические отчёты и расширенный Java scope | `samples/stress/inputs`, 8 файлов |
| `samples/scope/Main.java` | Независимая программа: abstract, интерфейс, do-while, instanceof, LinkedList, Iterator, static-блок, record, enum, дженерики, Optional, Stream | `samples/scope/inputs`, 8 файлов |

Для scope-примера проверяются пустой ввод, один элемент, дубли, границы, отрицательные числа, неправильный токен с кириллицей, выход за диапазон и большой набор. Интеграционные тесты выполняют граф → анализ → оптимизацию → декомпозицию → компиляцию → сравнение stdout/stderr/кода выхода в отдельных JVM.

## Поддерживаемый Java scope и ограничения

Парсер принимает конструкции JavaParser BLEEDING_EDGE; выполнение ограничено возможностями JDK 21. Поддерживаются пользовательские типы, интерфейсы, abstract, конструкторы, статические и экземплярные инициализаторы, поля, массивы, условия, switch, for/foreach/while/do-while, break/continue/return, исключения, консольный UTF-8 ввод/вывод, коллекции java.util, Formatter, Optional. Record, enum, дженерики, лямбды и Stream разбираются; выражения и Stream-цепочки показываются в составе операторов, без отдельного узла для каждой операции внутри лямбды.

Автоматические преобразования ограничены распознанными шаблонами:

- List.contains в цикле → индекс HashSet; некоторые вложенные циклы сопоставления по ключу → HashMap. Порядок совпадений сохраняется.
- Последовательный `stream().filter(x -> list.contains(x)).count()/toList()` → индекс HashSet для списка параметра с типом String или стандартной обёрткой. Ленивые и побочные эффекты в цепочке исключаются из этого шаблона.
- LONG_METHOD/HIGH_CYCLOMATIC → извлечение непрерывного блока с явными типами, максимум одним выходным значением. Return/yield/метки и выходящие наружу break/continue могут препятствовать извлечению; локальные переходы внутри переносимого цикла допустимы.
- Дубли методов → делегирование; некоторые повторные условия → общий метод.
- Декомпозиция выделяет статические вложенные классы и распределяет статические методы по Parser/Analyzer/Optimizer. При отсутствии подходящих групп пытается выделить часть длинного метода. При ошибке сборки возвращает исходный проект с объяснением. Произвольное разделение ответственности по смыслу не гарантируется.

Ссылочное `==` не переписывается автоматически: сравнение идентичности может быть намеренным. Условия с полями, сложные зависимости типов/состояния, произвольные Stream-цепочки и неизвестные конструкции могут требовать ручной правки. Необязательный LLM-режим API требует явного allowLlm и настройки LLM_API_KEY/LLM_API_URL/LLM_MODEL; стандартный интерфейс использует шаблоны.

Big-O — эвристика по циклам, типам переменных и некоторым Stream-callback. Это не формальный анализ: нет полного разрешения символов и межпроцедурного анализа, не все границы циклов распознаются, распределение ключей и размер результата индекса влияют на реальную сложность. Оценка «после» является прогнозом. Ускорение берётся только из успешного отчёта запуска; включает накладные расходы JVM, зависит от входа и не является гарантией производительности.

Quality Gate подтверждает совпадение только на выполненных входах, а не на всех возможных программах/данных. Клиент использует EXACT; API также предоставляет SORTED_LINES и MASKED. Для недетерминированных программ нужны осмысленные тесты и режим сравнения. Непрошедший кандидат не устанавливается при автооптимизации; ручные изменения остаются под контролем пользователя.

Многопоточность, рефлексия, сеть, файловые операции и java.time вне scope кейса. Отдельная JVM ограничена временем и памятью; это не защищённая граница для запуска враждебного кода. Разворачивайте демо локально или в изолированной среде.

## Проверки

```sh
cd server
./mvnw test
```

```sh
cd client
npm ci
npm test
npm run build
```

CI запускает серверные тесты и клиентские тесты/production-сборку. Клиентские регрессии проверяют отсутствие ложных PASSED, ошибки сборки, многофайловую синхронизацию, откат кандидата, измеренное ускорение и обработку SSE. Итоги доработки и связь со сверкой — в `docs/SPEC_RECONCILIATION.md`.

## Архитектура и API

`parser` хранит AST и соответствие методов/операторов узлам графа. `analyzer` формирует диагностику. `optimizer` выполняет шаблонные правки и декомпозицию. `sandbox` компилирует проекты и запускает отдельные JVM, сравнивая stdout, stderr и exit code. Zustand хранит дерево проекта, вкладки, исходный набор, граф и отчёт проверки.

Основные endpoints: POST `/api/graph`, `/api/graph/mutate`, `/api/analysis`, `/api/optimize`, `/api/decompose`, `/api/run`, `/api/verify`, `/api/verify/stream`; GET `/api/health`, `/api/verify/report`. JSON-контракты — `docs/API_CONTRACT.md`, подробное описание — `docs/ARCHITECTURE_AND_SPEC.md`. Последний отчёт доступен через API и сохраняется как verification_report.json.
